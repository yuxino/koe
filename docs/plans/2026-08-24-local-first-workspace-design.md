# Koe Local-First Workspace Design

## Product direction

Koe should feel like a quiet subtitle instrument, not a developer console. The side panel becomes a reading-first workspace: a compact brand and session header, one clear session action, three frequently used display preferences, and a transcript that owns the remaining height. Empty, preparing, gesture-required, live, and failed states are expressed in plain language near the action that resolves them. Copy and clear remain available for the transcript; diagnostic-log controls leave the normal interface. Technical details continue to exist in the background ring buffer for development and automated tests, but are no longer part of the user’s everyday workflow.

The visual direction is refined editorial minimalism. Koe uses neutral black, warm white, and restrained gray for almost the entire interface. The coral already present in the avatar is used sparingly for the current state and primary action. There are no gradients, decorative card grids, glass effects, or oversized bordered empty boxes. Subtitle text receives the strongest typographic hierarchy, timestamps become quiet metadata, and stable rows are separated by spacing and hairlines instead of individual cards. The panel must remain comfortable from 300 to 480 pixels wide and at short browser heights.

## Settings and startup

The browser remains the source of truth while it exists. `chrome.storage.local` continues to contain the DashScope API Key and all ordinary preferences. The API Key is explicitly excluded from every native backup. A small allow-listed preference document—translation, original visibility, capture mode, overlay visibility, overlay size, and initialization version—is mirrored by Koe Helper under the user’s Application Support directory. On a fresh extension profile, the background asks Helper for this document before applying defaults. On an existing profile, browser values win and refresh the native mirror. If Helper is unavailable, Koe simply uses browser storage.

Translation defaults to on, the overlay defaults to on, and the local-first mode becomes the default for a fresh install. Existing explicit choices are preserved. Native translation capability becomes tri-state (`unknown`, `available`, `unavailable`) so a cold service-worker start cannot turn off a saved translation preference before Helper finishes its handshake. Only an explicit `unavailable` result disables the local translation control. Changing a preference updates the interface immediately and schedules a native mirror; it never writes or exports the API Key.

## Local-first source routing

The existing HLS path remains the best path. When a playable HLS address is available, Helper reads only bounded media windows, prepares accurate Whisper cues ahead of playback, and keeps using the video’s absolute clock. When no HLS candidate appears after a short discovery window, Koe no longer ends in a technical “DASH/MP4 unsupported” error. It changes the same local session to a local-live pipeline.

Local-live requires Chromium tab-audio authorization. Automatic HLS sessions remain click-free; a non-HLS site shows a calm “one click required” state and a visible toolbar indicator until the user clicks Koe or presses Option-K. The offscreen page then captures 16 kHz mono PCM without requiring a DashScope key, batches it locally, and forwards base64 PCM chunks through the service worker’s existing Native Messaging port. Helper builds short overlapping WAV windows, runs the already-installed Whisper model, deduplicates overlap, and returns stable cues. Translation remains local through Apple Translation when available. No local-live audio or transcript is uploaded.

The initial local-live window is deliberately short for first-result latency; later windows are longer for recognition quality. The stream keeps a bounded buffer and processes one Whisper window at a time. Stop, seek, tab handoff, extension reload, and media replacement invalidate the old job/epoch so late native results cannot reappear over a new video. HLS and local-live share the same user-facing “本地优先” choice; pipeline details are shown as status, not exposed as another mode setting.

## Failure handling and verification

Errors are separated into three classes. A required user gesture is not an error and uses a neutral pending state. Recoverable failures—Helper unavailable, model preparation, temporary media read failure—show one short action-oriented sentence and keep the transcript. Terminal failures stop the affected session, clear queued audio, and leave a retry action. Detailed internal error codes remain in diagnostic logs without subtitle text. The toolbar badge uses neutral preparation for gesture-required state, `ON` for an active pipeline, and `!` only for a genuine failure.

Verification is layered. JavaScript tests cover default migration, native preference merge precedence, cold-start translation capability, non-HLS fallback selection, gesture gating, PCM forwarding, stop/race behavior, and removal of visible debug controls. Swift core checks cover preference normalization, bounded PCM windowing, WAV framing, overlap timing, and malformed audio rejection. Existing session, timeline, translation, transcript, overlay, and HLS suites must remain green. Visual QA uses the real extension page at narrow and wide side-panel sizes and checks idle, preparing, live transcript, settings-open, gesture-required, and error states. Finally, ego-lite runs the supplied YouTube video to verify that it offers or starts local-live instead of reporting an HLS compatibility error, while an HLS fixture verifies that the existing ahead-of-playback path is unchanged.
