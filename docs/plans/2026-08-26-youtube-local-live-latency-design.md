# YouTube 本地实时字幕低延迟设计

## 背景

目标视频 `D4b-BoRPz2I` 的真实浏览器基线显示，热模型稳态字幕约晚于对应 cue 结束时间 0.7–2.7 秒，但更新会成团出现；20.4 秒样本中只有 5 次原文更新，最长一次可感知停顿约 7.6 秒。启动路径还会固定等待 1.8 秒媒体探测，再收满 4 秒 PCM，之后才准备并运行 Whisper。

## 目标

- 可信的标签页音频授权已经存在时，不再空等 1.8 秒。
- 第一段 PCM 收满 2 秒即可开始识别；稳态仍保留 4 秒上下文和 1.5 秒重叠，避免明显损伤歌词与连续语音质量。
- 收音期间并行准备 large-v3，使模型加载不再串在首窗之后。
- 慢推理时只保留最近 6 秒 PCM，主动丢弃已过时的历史窗口，避免延迟随播放时间持续增长。
- 保留既有媒体时间锚、seek/换页 epoch 隔离、同语言跳过翻译和完整 HLS 精准路径。

## 方案

### 浏览器启动路径

`START_CAPTURE` 已在用户手势期间保存 `tabCapture` stream ID。`receiveMediaContext` 发现页面没有可用 HLS，但该 ID 已存在时，立即进入本地实时 fallback；只有没有授权 ID 时才保留 1.8 秒探测窗口与提示流程。

### PCM 窗口与背压

把 `PCMStreamBuffer` 默认首窗从 4,000ms 改为 2,000ms，稳态窗口仍为 4,000ms、重叠 1,500ms。默认最大缓存从 30,000ms 改为 6,000ms。现有裁剪逻辑在超过上限时前移下一窗起点，因此慢推理只处理最新的完整窗口，不追赶陈旧字幕。

### 模型准备

`streamStart` 创建流会话后立即启动独立的 `Task` 调用 `transcriber.prepare()`。Native Messaging actor 不等待这个任务，因此仍可持续接收 PCM。首窗处理仍调用同一个幂等的 `prepare()` 作为 readiness/error barrier。模型属于 Helper 生命周期的共享资源：普通停止或换页不取消预载，只有 Helper 关闭时才取消；预载任务本身不读取会话状态、也不发送状态或错误，因此不会污染新会话。

本轮不降低模型，也不缩短稳态上下文。首次实机验收发现歌词/伴奏会触发 WhisperKit 默认最多 5 次温度回退（共 6 次 decode），并且首个伴奏窗口可能把错误语言锁定整段媒体。因此实时 profile 将回退次数限制为 1（最多 2 次 decode），且每个实时窗口重新检测语言；HLS 精准 profile 继续保留 5 次回退与媒体级语言复用。若 p95 仍高，再单独评估 3 秒稳态窗。

### 字幕显示

本轮先不引入新的页面排队器。媒体时间字幕若晚到，页面已有过期丢弃与固定可读时长；再增加排队会把识别延迟变成显示延迟。先通过更早首窗和有界积压减少批次停顿，再用同一视频判断是否仍需逐 cue 调度。

## 测试

- Swift core check：默认首窗精确为 2 秒，第二窗保持 4 秒/1.5 秒重叠；默认缓存不超过 6 秒，慢消费者会跳到最新完整窗口。
- JS local-live test：`offlineMissingMediaSince` 刚创建但已有 stream ID 时，第一次媒体上下文就启动 fallback；无 ID 时仍等待并提示授权。
- Swift build/check：Core checks、helper 双目标构建与现有全量测试。
- 真实浏览器：重新安装后在同一 YouTube 视频测首条与至少 60 秒稳态；要求热模型 p50 小于 2.5 秒、p95 小于 4 秒、延迟无持续增长，并验证 seek/SPA 切换、字幕可见与同语言跳过翻译。

## 回退

所有变更都在本地实时 fallback 路径内。若首窗质量下降，可独立把 bootstrap 恢复到 4 秒；若跳窗过于激进，可把最大缓存从 6 秒提高到 8 秒，不影响协议或页面存储。
